# 00. ビジョンと課題設定

> **English summary**: Why a task/workflow system, not another chatbot. Chat
> conflates four separable concerns — conversation, durable state, multi-actor
> approval, and capability scoping — and forces every collaborator through one
> linear UI. We instead model work as durable, linkable task entities driven by
> agent-executed workflows, with explicit approval gates and per-actor tool scopes.

## 1. 出発点：チャット UI の限界

現在の LLM 活用は「チャット」が主流です。チャットは探索的な対話には優れていますが、
**組織の継続的な業務**を載せると次の構造的な問題が表面化します。

### 課題 A：第三者の巻き込みが苦手

ある作業の途中で「会計担当者の承認がほしい」「他部署の確認がほしい」という状況になったとき、
チャットでは**その人物を会話そのものに連れてくる**しかありません。すると、

- 承認者は本来関係のない長大な会話の文脈を読まされる（UI の制約を強く受ける）。
- 承認という行為が「会話の発言」に埋もれ、構造化されず、後から追えない。
- 並行する複数の作業が一本の会話に直列化され、混線する。

本来「承認」は、**会話とは独立した、構造化された小さな意思決定**であるべきです。

### 課題 B：状態が会話に溶けている

チャットの状態は「これまでの発言の履歴」です。これは、

- 「今この案件はどの段階か（事前申請済みか、承認待ちか、精算済みか）」を機械可読に持てない。
- 数日〜数週間にわたって**中断・再開**する長時間プロセスを扱えない。
- 同じ案件に複数人・複数エージェントが**非同期に**関わることを扱えない。

### 課題 C：繰り返しを表現できない

「毎月 1 日と 15 日に定例の支払いをする」「前回処理した日から今日までの分をまとめて精算する」
といった**定期・区間処理**は、対話の一回性とは相容れません。

### 課題 D：実行者ごとの権限差を扱えない

「この人は経費を 2 万円まで承認できる」「このエージェントは金額照会はできるが送金はできない」
といった**実行者ごとのツール利用範囲**は、チャットの自由対話では安全に表現・強制できません。

## 2. 着想：仕事を「タスク」という石として置く

これらの課題の根は一つです。**会話に、状態・承認・繰り返し・権限という別種の関心を
押し込んでいる**こと。解決策は、それらを会話から引き剥がし、独立した第一級の存在にすること。

中心に据えるのは **タスク（Task）** という永続エンティティです。Git の Issue のように、

- それ自体が URL を持ち、可視で、参照でき、議論を貼り付けられる「石」。
- 互いに **リンク** でき、**サブタスク** を持てる。
- ひとつの「意図」を表す。例：
  - 「イベントのサムネイルを更新したい」
  - 「この出品について問い合わせ対応したい」
  - 「今月の交通費を精算したい」
  - 「外部の取引先に連絡を取りたい」

タスクは静的なメモではありません。タスクには **ワークフロー（処理の流れ）** を結びつけられ、
その各ステップを **LLM エージェント** が **外部ツール** を叩いて進めます。

## 3. プロダクトの一文定義

> **永続的なタスク・エンティティを、権限つきの LLM エージェントが外部ツールを使って
> 段階的に進める。人間の承認はワークフロー上の明示的なゲートとして表現され、
> 定期業務は区間処理として自動化される。チャットは入力手段の一つに過ぎない。**

## 4. 具体例で見る「あるべき体験」

### 例：交通費の精算（詳細は [08-reference-workflows.md](./08-reference-workflows.md)）

1. ユーザーが「○○から△△までの交通費を申請したい」というタスクを作る。
2. 担当エージェントが**経路・運賃を照会するツール**を使い、金額を算出する。
3. エージェントが「この内容で**事前申請**しますか？」と確認（Yes/No）を出す。
4. Yes を押すと事前申請が投稿され、**タスクの連鎖が一旦停止し**、会計担当者の承認待ちになる。
5. 会計担当者が承認すると、連鎖は「事前承認済み」の状態で止まったまま保持される。
6. 後日、実際に移動が済んだら「精算したい」を実行。交通費は領収書不要というルールに従い、
   「精算する」ボタンを押すと**精算（支払い）処理**が発火する。

ここでの要点：

- **承認は会話ではなくゲート**：会計担当者は長い会話を読まず、構造化された 1 件の申請を見る。
- **状態は機械可読**：いつでも「事前承認済み・精算待ち」のような状態が分かる。
- **権限はツール単位**：金額照会と送金は別のツールであり、叩ける主体が異なる。
- **中断と再開**：承認待ちの間、プロセスは計算資源を消費せず眠り、承認で目覚める。

## 5. 適用範囲（経理に限らない）

同じ構造は、承認や外部作用を伴うあらゆる業務に適用できます。

- 経費・支払い・精算（本ドキュメントの主たる例）
- 外部（取引先・他団体）との連絡・交渉タスク
- 出品・公開物の更新（サムネ更新、掲載内容の変更）
- 定期的なレポート生成・締め処理

## 6. 設計上の北極星（ガイドライン）

1. **会話と状態を分離する。** タスクが状態の正本であり、会話はその上の注釈。
2. **承認を第一級にする。** 承認は構造化されたゲートであり、会話の発言ではない。
3. **権限は最小・縮小・短命。** 委譲のたびに権限は狭まる（attenuation）。
4. **中断・再開を前提にする。** プロセスは数日眠っても安全に再開できる。
5. **監査可能性を常に持つ。** 誰が・いつ・どのツールを・どの権限で叩いたかを追える。
6. **技術非依存に設計する。** まず概念を固め、実装技術は後で選ぶ。
